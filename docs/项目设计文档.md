# 红色文化学习打卡系统 — 项目设计文档

> 本文档涵盖：系统概述、数据库设计（建表语句与说明）、后端函数（路由/接口）清单与功能对应表、核心业务逻辑、项目结构、运行部署说明。

---

## 一、系统概述

### 1.1 项目简介

红色文化学习打卡系统是一个 B/S 架构的 Web 应用，面向两类角色：

| 角色 | 主要功能 |
|------|----------|
| 普通用户 | 注册登录、浏览红色景点、查看红色历史、学习打卡（写心得）、查看我的打卡记录、修改心得、删除打卡、查看公告、查看热门景点排行、管理个人信息 |
| 管理员 | 登录后台、仪表盘统计、景点管理（增删改查）、公告管理（增删改查）、查看所有用户 |

### 1.2 技术栈

| 层次 | 技术 | 说明 |
|------|------|------|
| 前端 | EJS 模板引擎 + HTML/CSS | 服务端渲染，公共头部/底部抽离 |
| 后端 | Node.js 22 + Express 4 | MVC 分层：routes（控制器）→ views（视图）→ db（模型） |
| 数据库 | MySQL 8.0（utf8mb4） | 5 张业务表，InnoDB 引擎支持事务与外键；管理员不建表 |
| 数据访问 | mysql2/promise 连接池 | Promise 风格，`pool` + `query()` 二次封装 |
| 密码安全 | bcryptjs | 哈希加盐，强度 10 轮 |
| 会话 | express-session | Cookie-Session 鉴权，有效期 1 天 |

### 1.3 运行环境

- 端口：`3000`（避开 80 与 8090，留给毕设其他子项目）
- 访问地址：`http://localhost:3000`
- 演示账号：
  - 普通用户：`test / 123456`
  - 管理员：`admin / 123456`

## 二、数据库设计

### 2.1 数据库与字符集

```sql
CREATE DATABASE red_culture_checkin
    DEFAULT CHARACTER SET utf8mb4
    COLLATE utf8mb4_unicode_ci;
```

### 2.2 数据表一览

| 序号 | 表名 | 中文名 | 记录说明 |
|------|------|--------|----------|
| 1 | `user` | 用户表 | 全部注册用户（含密保、资料字段） |
| 2 | `announcement` | 公告表 | 系统公告 |
| 3 | `scenic_spot` | 景点表 | 红色景点信息（含图片与热门判定字段） |
| 4 | `check_in_record` | 打卡记录表 | 用户与景点的打卡关联（核心业务表） |
| 5 | `hero_figure` | 革命人物表 | 景点关联的革命人物（图片展示用） |

> 管理员不建表：系统仅 1 名管理员，账号密码固定在 `config/admin.js`。

### 2.3 建表语句与字段说明

#### （1）用户表 `user`

```sql
CREATE TABLE user (
    user_id           INT PRIMARY KEY AUTO_INCREMENT COMMENT '用户ID',
    username          VARCHAR(50)  UNIQUE NOT NULL COMMENT '用户名',
    password          VARCHAR(100) NOT NULL COMMENT '密码(bcrypt)',
    security_question VARCHAR(100) DEFAULT NULL COMMENT '密保问题(找回密码用)',
    security_answer   VARCHAR(100) DEFAULT NULL COMMENT '密保答案',
    real_name         VARCHAR(50)  DEFAULT NULL COMMENT '真实姓名',
    gender            VARCHAR(10)  DEFAULT NULL COMMENT '性别',
    phone             VARCHAR(20)  DEFAULT NULL COMMENT '电话号码',
    location          VARCHAR(100) DEFAULT NULL COMMENT '所在地',
    score             INT          DEFAULT 0 COMMENT '学习积分,打卡+1/删除-1',
    register_time     DATETIME     DEFAULT CURRENT_TIMESTAMP COMMENT '注册时间'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户表';
```

| 字段 | 类型 | 约束 | 功能说明 |
|------|------|------|----------|
| user_id | INT | 主键、自增 | 用户唯一标识 |
| username | VARCHAR(50) | 唯一、非空 | 登录账号，注册/改用户名时查重 |
| password | VARCHAR(100) | 非空 | bcrypt 哈希后的密码，非明文 |
| score | INT | 默认 0 | 学习积分：打卡 +1，删除打卡 -1（下限 0） |
| register_time | DATETIME | 默认当前时间 | 注册时间，个人信息页展示 |

#### （2）管理员账号说明

系统仅设置一名管理员，管理员不建数据库表，账号与密码固定存放于 `config/admin.js`：账号 `admin`，密码以 bcrypt 哈希形式保存，登录时由 `verify()` 函数比对，同样不出现明文。

这样设计的考虑：管理员是系统的运维角色而非业务数据，没有新增、删除管理员的需求，独立建表没有实际意义；将其收敛到配置文件中，可以减少一张表和相应的查询逻辑，同时密码仍走 bcrypt 加密，兼顾了安全性与简洁性。

#### （3）公告表 `announcement`

```sql
CREATE TABLE announcement (

    publish_date    DATE         COMMENT '发布日期',
    remark          VARCHAR(255) DEFAULT '' COMMENT '备注'

```

| 字段 | 类型 | 约束 | 功能说明 |
|------|------|------|----------|
| announcement_id | INT | 主键、自增 | 公告唯一编号，支持按编号查询 |
| title | VARCHAR(100) | 非空 | 公告标题，支持模糊查询 |
| content | TEXT | — | 公告正文 |
| publish_date | DATE | — | 发布日期，列表按此倒序 |
| remark | VARCHAR(255) | 默认空串 | 备注 |

#### （4）景点表 `scenic_spot`（含热门判定）

```sql
CREATE TABLE scenic_spot (
    scenic_id      INT PRIMARY KEY AUTO_INCREMENT COMMENT '景点编号',
    scenic_name    VARCHAR(100) NOT NULL COMMENT '景点名称',
    location       VARCHAR(200) COMMENT '地理位置',
    description    TEXT         COMMENT '景点描述',
    red_history    TEXT         COMMENT '红色历史',
    check_count    INT          DEFAULT 0 COMMENT '打卡次数,>=10 即热门'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='景点表';
```

| 字段 | 类型 | 约束 | 功能说明 |
|------|------|------|----------|
| scenic_id | INT | 主键、自增 | 景点编号，支持按编号查询 |
| scenic_name | VARCHAR(100) | 非空 | 景点名称，支持模糊查询 |
| location | VARCHAR(200) | — | 地理位置 |
| description | TEXT | — | 景点描述 |
| red_history | TEXT | — | 红色历史（学习内容核心） |
| check_count | INT | 默认 0 | 累计打卡次数，**>=10 判定为热门** |

#### （5）打卡记录表 `check_in_record`（核心业务表）

```sql
CREATE TABLE check_in_record (
    check_id    INT PRIMARY KEY AUTO_INCREMENT COMMENT '打卡记录ID',
    user_id     INT  NOT NULL COMMENT '用户ID',
    scenic_id   INT  NOT NULL COMMENT '景点ID',
    check_time  DATETIME DEFAULT CURRENT_TIMESTAMP COMMENT '打卡时间',
    experience  TEXT COMMENT '打卡心得',
    FOREIGN KEY (user_id)   REFERENCES user(user_id)        ON DELETE CASCADE,
    FOREIGN KEY (scenic_id) REFERENCES scenic_spot(scenic_id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='打卡记录表';

-- 查询性能索引
CREATE INDEX idx_record_user   ON check_in_record(user_id);
CREATE INDEX idx_record_scenic ON check_in_record(scenic_id);
CREATE INDEX idx_record_time   ON check_in_record(check_time);
```

| 字段 | 类型 | 约束 | 功能说明 |
|------|------|------|----------|
| check_id | INT | 主键、自增 | 打卡记录编号 |
| user_id | INT | 外键 → user | 打卡人，级联删除 |
| scenic_id | INT | 外键 → scenic_spot | 打卡景点，级联删除 |
| check_time | DATETIME | 默认当前时间 | 打卡时间 |
| experience | TEXT | — | 打卡心得（可修改，不可为空） |

### 2.4 表间关系（E-R 说明）

```
user (1) ────< check_in_record >──── (1) scenic_spot
                 [打卡记录表]
scenic_spot (1) ────< (N) hero_figure   [景点关联革命人物，级联删除]
announcement：独立表
管理员：不建表，账号密码固定于 config/admin.js
```

- 一个用户可以打卡多个景点，一个景点可以被多个用户打卡 → **多对多**，`check_in_record` 为中间表
- 删除用户或删除景点时，其关联打卡记录**级联删除**（`ON DELETE CASCADE`）
- 删除景点时，其关联革命人物同样级联删除

## 四、核心业务逻辑

### 4.1 打卡事务（三大表联动）

```
用户提交打卡 POST /checkin (scenic_id, experience)
        │
        ▼
┌─ 开启事务 beginTransaction ─────────────────────┐
│  ① INSERT INTO check_in_record (写打卡记录)      │
│  ② UPDATE user SET score = score + 1            │
│  ③ UPDATE scenic_spot SET check_count + 1       │
│  ④ SELECT score → 同步 req.session.user.score    │
│  ⑤ COMMIT（失败则 ROLLBACK）                     │
└─────────────────────────────────────────────────┘
```

- **原子性**：三表更新要么全部成功，要么全部回滚，杜绝"加了积分但没记录"的数据不一致
- **热门景点**：`check_count` 累计 ≥ 10 自动进入热门排行（查询时判定，无冗余字段）

### 4.2 密码安全（bcryptjs）

| 环节 | 函数 | 说明 |
|------|------|------|
| 注册 | `bcrypt.hashSync(password, 10)` | 10 轮加盐哈希后入库 |
| 登录 | `bcrypt.compareSync(password, hash)` | 比对明文与哈希 |
| 改密码 | 原密码 compare → 新密码 hash | 双重校验 |

### 4.3 会话鉴权（express-session）

- 登录成功后把 `user_id / username / score`（或管理员 `username`）写入 session
- 全局中间件将 `user / admin / flash` 注入所有视图模板
- `requireUser` / `requireAdmin` 中间件统一拦截未授权访问
- 退出登录 `req.session.destroy()` 彻底销毁会话

### 4.4 一次请求的完整链路

```
浏览器 → Express 中间件(bodyParser/session/静态资源)
       → 路由分发(app.js 挂载 6 个模块)
       → 鉴权中间件(requireUser/requireAdmin)
       → 路由处理函数(await query / pool 事务)
       → mysql2 连接池 → MySQL
       → EJS 渲染视图 → 返回 HTML
```

## 六、运行与部署

### 6.1 本地运行步骤

```bash
# 1. 确保 MySQL 8 已启动（Windows 服务 MySQL80）
net start MySQL80

# 2. 初始化数据库（首次）
mysql -u root -p123456 < sql/init.sql

# 3. 安装依赖（首次）
npm install

# 4. 启动服务
node app.js
# 看到 "✅ MySQL 连接成功" 即启动成功

# 5. 浏览器访问
# http://localhost:3000
```

### 6.2 数据库连接配置（config/db.js）

| 配置项 | 默认值 | 环境变量覆盖 |
|--------|--------|--------------|
| host | localhost | `DB_HOST` |
| port | 3306 | `DB_PORT` |
| user | root | `DB_USER` |
| password | 123456 | `DB_PASS` |
| database | red_culture_checkin | `DB_NAME` |

> 部署到云服务器时，可通过环境变量注入数据库配置，无需改代码。

### 6.3 已修复的关键问题记录

| 问题 | 原因 | 修复方案 |
|------|------|----------|
| 登录提示"密码错误" | init.sql 预置哈希为无效值 | 重新生成 bcrypt 哈希并同步数据库与脚本 |
| 打卡时服务崩溃 `TypeError: cb is not a function` | `config/db.js` 用回调版 `mysql2`，而路由用 Promise 语法，两套 API 混用 | db.js 改用 `mysql2/promise`，统一为 async/await |
