# 红色文化学习打卡系统项目开发文档

## 一、需求分析

### 1.1 项目背景

红色文化是中国革命和建设过程中形成的重要精神财富，对高校学生进行红色文化教育具有重要意义。传统的红色文化学习方式多以课堂讲授和线下参观为主，形式较为单一，学生参与度不高。基于此，本项目设计并实现了一套红色文化学习打卡系统，通过线上景点浏览、红色历史学习和打卡心得记录等功能，提升学生参与红色文化学习的积极性和主动性。

### 1.2 用户角色与功能需求

系统主要面向两类用户角色，分别是普通用户和管理员，两类角色的功能需求存在明显差异。

普通用户的功能需求包括：账号注册与登录、浏览红色景点信息、查看景点红色历史、提交打卡心得、查看和修改个人打卡记录、查看系统公告、浏览热门景点排行以及管理个人信息等。

管理员的功能需求包括：登录后台管理系统、查看系统数据统计、管理红色景点信息、发布和管理公告、查看所有注册用户等。

### 1.3 功能模块划分

根据上述需求，系统可以划分为五个主要功能模块：

- 用户认证模块：负责用户注册、登录、退出和权限区分。
- 景点浏览模块：负责展示景点列表、景点详情、热门排行等功能。
- 打卡管理模块：负责打卡记录的提交、修改、删除和查询。
- 公告管理模块：负责公告的展示以及管理员对公告的增删改查。
- 后台管理模块：负责管理员仪表盘统计、用户列表查看和景点公告管理。

## 二、项目规划

### 2.1 技术架构

本系统采用B/S架构，用户通过浏览器即可访问全部功能，无需安装额外客户端。服务端采用Node.js配合Express框架处理请求，前端采用EJS模板引擎进行服务端渲染，数据库采用MySQL 8.0存储业务数据。整体架构清晰，前后端职责分离，便于后续维护和扩展。

### 2.2 开发环境

开发过程中使用的主要软件和工具版本如下：

- 操作系统：Windows 11
- 开发工具：WebStorm 2024
- Node.js版本：22.22.2
- 数据库：MySQL 8.0
- 数据库连接工具：MySQL命令行客户端 / WebStorm Database插件

项目运行端口设置为3000，本地访问地址为http://localhost:3000。系统预置了两个演示账号，普通用户为test/123456，管理员为admin/123456。

### 2.4 数据库规划

根据功能需求分析，数据库需要存储用户信息、景点信息、公告信息和打卡记录信息。经过梳理，数据库共设计五张数据表，分别为user用户表、announcement公告表、scenic_spot景点表、check_in_record打卡记录表和hero_figure革命人物表。其中打卡记录表作为用户和景点之间的关联表，记录用户的打卡行为和心得内容。管理员不建表，账号密码固定在配置文件中管理。

## 三、原型设计

### 3.1 用户端页面原型

用户端页面围绕普通用户的使用流程设计，主要页面包括：

- 登录页：提供用户名、密码输入框和角色选择，未注册用户可跳转注册页。
- 注册页：收集用户名、密码、确认密码等注册信息。
- 景点列表页：以卡片或表格形式展示所有景点，支持按名称和编号搜索。
- 景点详情页：展示景点名称、地理位置、景点描述、红色历史，并提供打卡入口。
- 打卡提交页：包含心得输入框，用户填写后提交打卡。
- 我的打卡页：展示当前用户的所有打卡记录，支持修改、删除和筛选。
- 公告列表页：展示系统公告，支持按标题和编号搜索。
- 热门景点页：展示打卡次数达到热门标准的景点排行。
- 个人信息页：展示用户ID、用户名、积分、注册时间，并提供修改用户名和密码的入口。

### 3.2 管理端页面原型

管理端页面面向管理员，主要页面包括：

- 管理员登录页：与普通用户共用登录入口，系统根据账号所属表自动判断角色。
- 后台仪表盘页：展示用户总数、景点总数、打卡总数、公告总数、热门景点数以及打卡次数前五的景点。
- 用户管理页：展示所有注册用户列表，支持按用户名和ID搜索。
- 景点管理页：管理员可对景点进行新增、编辑和删除操作。
- 公告管理页：管理员可发布公告、编辑和删除已有公告。

### 3.3 页面跳转关系

未登录用户访问系统时，会被重定向到登录页。登录成功后，普通用户进入景点列表页，管理员进入后台仪表盘页。普通用户在景点详情页点击打卡按钮后进入打卡提交页，提交成功后返回景点详情页或我的打卡页。管理员通过顶部导航在各管理功能之间切换。所有需要登录才能访问的页面都设有权限校验，未授权访问会被重定向到登录页。

## 四、前端开发

### 4.1 前端技术说明

本项目前端采用服务端渲染方式，页面由Express后端通过EJS模板引擎动态生成后返回给浏览器。这种方式适合内容型管理系统，能够减少前后端交互复杂度，同时有利于搜索引擎抓取页面内容。

页面交互主要使用原生HTML表单提交和超链接跳转，不依赖复杂的前端框架。对于一些简单的确认操作，如删除打卡记录，使用JavaScript的confirm方法进行二次确认，避免误操作。

### 4.2 模板组织结构

视图模板统一存放在views目录下，按照功能模块进一步细分。公共头部和底部抽离为_header.ejs和_footer.ejs，其他页面通过include方式引入，保证全站导航和样式一致。

主要模板文件及其对应页面如下：

- login.ejs：登录页
- register.ejs：注册页
- profile.ejs：个人信息页
- scenic/list.ejs：景点列表页
- scenic/detail.ejs：景点详情页
- scenic/hot.ejs：热门景点排行页
- checkin/write.ejs：打卡提交页
- checkin/my.ejs：我的打卡页
- checkin/edit.ejs：修改心得页
- announcement/list.ejs：公告列表页
- admin/dashboard.ejs：管理员仪表盘
- admin/users.ejs：用户管理页
- admin/scenic-list.ejs / scenic-edit.ejs：景点管理页
- admin/announcement-list.ejs / announcement-edit.ejs：公告管理页

### 4.3 公共组件

_header.ejs负责渲染顶部导航栏，根据当前登录用户角色显示不同的菜单项。普通用户看到景点、热门景点、公告、我的打卡和个人信息入口；管理员则看到仪表盘、景点管理、公告管理和用户管理入口。未登录状态下只显示登录和注册链接。

_footer.ejs渲染页面底部版权信息，保持简洁。

### 4.4 样式设计

样式文件位于public/css/style.css，全局采用统一的字体、颜色和间距规范。页面布局采用常见的头部、主体、底部三层结构，主体内容居中显示。表单元素统一设置边框、圆角和焦点样式，按钮区分主按钮和危险按钮，提升用户操作体验。表格样式用于景点列表、打卡记录和管理后台数据展示，表头加粗，行与行之间有明显分隔。

## 五、后端开发

### 5.1 数据库设计

数据库采用MySQL 8.0，字符集设置为utf8mb4以支持完整的中文字符和表情符号。数据库创建语句如下：

```sql
CREATE DATABASE red_culture_checkin
    DEFAULT CHARACTER SET utf8mb4
    COLLATE utf8mb4_unicode_ci;
```

五张数据表的具体设计如下：

用户表user用于存储所有注册用户的基本信息，包含用户ID、用户名、密码、积分和注册时间等字段。其中密码字段存储的是bcrypt加密后的哈希值，而不是明文密码。

系统仅设置一名管理员，管理员不建数据库表，账号与密码固定存放在config/admin.js中，密码同样以bcrypt哈希形式保存，登录时由专门的校验函数比对。这样设计的原因是：管理员属于系统的运维角色而非业务数据，没有新增或删除管理员的需求，独立建表没有实际意义，收敛到配置文件可以减少一张表和对应的查询逻辑。

公告表announcement用于存储系统公告，包含公告编号、标题、内容、发布日期和备注字段。

景点表scenic_spot用于存储红色景点信息，包含景点编号、名称、地理位置、描述、红色历史和打卡次数字段。打卡次数达到10次及以上的景点被视为热门景点。

打卡记录表check_in_record用于记录用户的打卡行为，包含记录ID、用户ID、景点ID、打卡时间和心得内容。该表通过外键与用户表和景点表关联，并设置了级联删除。

### 5.2 数据表结构

用户表user的建表语句：

```sql
CREATE TABLE user (
    user_id           INT PRIMARY KEY AUTO_INCREMENT COMMENT '用户ID',
    username          VARCHAR(50)  UNIQUE NOT NULL COMMENT '用户名',
    password          VARCHAR(100) NOT NULL COMMENT '密码',
    security_question VARCHAR(100) DEFAULT NULL COMMENT '密保问题',
    security_answer   VARCHAR(100) DEFAULT NULL COMMENT '密保答案',
    real_name         VARCHAR(50)  DEFAULT NULL COMMENT '真实姓名',
    gender            VARCHAR(10)  DEFAULT NULL COMMENT '性别',
    phone             VARCHAR(20)  DEFAULT NULL COMMENT '电话号码',
    location          VARCHAR(100) DEFAULT NULL COMMENT '所在地',
    score             INT          DEFAULT 0 COMMENT '学习积分',
    register_time     DATETIME     DEFAULT CURRENT_TIMESTAMP COMMENT '注册时间'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户表';
```

公告表announcement的建表语句：

```sql
CREATE TABLE announcement (
    announcement_id INT PRIMARY KEY AUTO_INCREMENT COMMENT '公告编号',
    title           VARCHAR(100) NOT NULL COMMENT '公告标题',
    content         TEXT         COMMENT '公告内容',
    publish_date    DATE         COMMENT '发布日期',
    remark          VARCHAR(255) DEFAULT '' COMMENT '备注'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='公告表';
```

景点表scenic_spot的建表语句：

```sql
CREATE TABLE scenic_spot (
    scenic_id      INT PRIMARY KEY AUTO_INCREMENT COMMENT '景点编号',
    scenic_name    VARCHAR(100) NOT NULL COMMENT '景点名称',
    location       VARCHAR(200) COMMENT '地理位置',
    description    TEXT         COMMENT '景点描述',
    red_history    TEXT         COMMENT '红色历史',
    image          VARCHAR(255) DEFAULT NULL COMMENT '景点图片文件名',
    check_count    INT          DEFAULT 0 COMMENT '打卡次数'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='景点表';
```

打卡记录表check_in_record的建表语句：

```sql
CREATE TABLE check_in_record (
    check_id    INT PRIMARY KEY AUTO_INCREMENT COMMENT '打卡记录ID',
    user_id     INT  NOT NULL COMMENT '用户ID',
    scenic_id   INT  NOT NULL COMMENT '景点ID',
    check_time  DATETIME DEFAULT CURRENT_TIMESTAMP COMMENT '打卡时间',
    experience  TEXT COMMENT '打卡心得',
    FOREIGN KEY (user_id)   REFERENCES user(user_id)        ON DELETE CASCADE,
    FOREIGN KEY (scenic_id) REFERENCES scenic_spot(scenic_id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='打卡记录表';

CREATE INDEX idx_record_user   ON check_in_record(user_id);
CREATE INDEX idx_record_scenic ON check_in_record(scenic_id);
CREATE INDEX idx_record_time   ON check_in_record(check_time);
```

### 5.3 路由与接口设计

后端路由按照功能划分为六个模块，统一在app.js中挂载。

认证模块routes/auth.js负责首页重定向、登录页面渲染、登录验证、注册页面渲染、注册处理、退出登录以及表单校验提示等功能。

景点模块routes/scenic.js同时服务于普通用户和管理员。普通用户可以查看景点列表、查看热门排行、查看景点详情和进入打卡页面；管理员可以对景点进行新增、编辑、删除和列表管理。

公告模块routes/announcement.js面向普通用户展示公告列表，面向管理员提供公告的增删改查功能。

打卡模块routes/checkin.js是系统的核心业务模块，负责提交打卡、查询我的打卡记录、修改打卡心得和删除打卡记录。提交和删除打卡涉及多张表更新，采用数据库事务保证数据一致性。

个人信息模块routes/user.js负责展示个人信息、修改用户名和修改密码。

管理员模块routes/admin.js负责仪表盘统计和用户列表查看。

### 5.4 核心功能实现

#### 5.4.1 提交打卡

用户提交打卡时，后端需要同时完成三项操作：在check_in_record表中插入一条新记录，在user表中将该用户的score字段加1，在scenic_spot表中将对应景点的check_count字段加1。为了保证这三项操作要么全部成功、要么全部失败，代码中使用数据库事务包裹整个流程。事务开启后依次执行插入和更新操作，全部成功则提交事务，任一操作失败则回滚事务。

#### 5.4.2 删除打卡

删除打卡与提交打卡相反，需要删除check_in_record表中的对应记录，并将user表的score字段减1，将scenic_spot表的check_count字段减1。删除前会先校验该记录是否属于当前登录用户，非本人记录不允许删除。同样采用事务保证数据一致性，并对减分操作做了下限保护，避免积分和打卡次数变为负数。

#### 5.4.3 密码安全

用户密码采用bcryptjs库进行哈希处理。注册和修改密码时，调用bcrypt.hashSync方法对明文密码进行10轮加盐哈希后再存入数据库。登录和修改密码验证时，调用bcrypt.compareSync方法比对用户输入的明文密码和数据库中存储的哈希值。整个过程中数据库不保存任何明文密码。

#### 5.4.4 会话管理

用户或管理员登录成功后，系统通过express-session将用户ID、用户名、积分等必要信息写入session。后续请求中，后端通过读取session判断用户身份和权限。普通页面需要requireUser中间件校验登录状态，管理页面需要requireAdmin中间件校验管理员身份。退出登录时调用req.session.destroy销毁会话。

### 5.5 安全机制

系统在多个层面考虑了安全性。首先是密码安全，全部使用bcrypt哈希存储。其次是SQL注入防护，所有数据库操作均使用参数化查询，避免直接拼接SQL语句。第三是权限控制，通过session和中间件拦截未授权访问，并在涉及个人数据修改和删除的操作中校验资源归属。第四是表单校验，注册和修改密码时对字段长度、格式和一致性进行了服务端校验。

### 5.6 运行与部署

本地运行项目的步骤如下：

第一步，确保MySQL服务已启动。Windows环境下可以通过服务管理器或命令行启动MySQL80服务。

第二步，初始化数据库。在命令行中执行：

```bash
mysql -u root -p123456 < sql/init.sql
```

第三步，安装项目依赖。在项目根目录下执行：

```bash
npm install
```

第四步，启动服务：

```bash
node app.js
```

服务启动成功后，在浏览器中访问http://localhost:3000即可使用系统。

数据库连接配置集中存放在config/db.js中，默认连接本地MySQL，数据库名为red_culture_checkin，用户名root，密码123456。部署到服务器时可以通过环境变量覆盖这些配置，无需修改代码。
